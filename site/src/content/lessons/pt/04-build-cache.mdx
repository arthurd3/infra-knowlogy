O build cache tem duas regras. A primeira é intuitiva; a segunda é a que
transforma um build de 2 segundos num de 50.

1. Uma camada é reaproveitada se **a instrução e as entradas dela** não mudaram.
2. Invalidou uma camada, **invalidam todas as seguintes** — mesmo as que não têm
   nada a ver com o que você mudou.

A segunda regra é o efeito cascata, e ela é inevitável: cada camada é construída
*em cima* da anterior. Se a base mudou, o que estava em cima dela já não é o
mesmo.

## Como a chave de cache é calculada

Depende da instrução:

- **`RUN`** — o cache olha para o **texto do comando**, não para o resultado.
  `RUN apt-get update` com o mesmo texto acerta o cache hoje, amanhã e daqui a um
  ano, mesmo que os repositórios tenham mudado inteiramente. É por isso que
  `update` e `install` precisam estar no mesmo `RUN`.
- **`COPY` / `ADD`** — o cache calcula um **checksum do conteúdo** dos arquivos.
  Metadado como data de modificação não conta; um arquivo tocado mas não alterado
  não invalida nada.
- **`ENV`, `LABEL`, `USER`, `WORKDIR`** — só o texto, e são baratas.

Compare os dois presets com **"o código-fonte"** marcado. É o cenário do dia a
dia — você editou um arquivo e vai buildar de novo:

- **Ordem boa**: o `COPY . .` vem depois do `npm ci`. O `npm ci` está acima da
  camada invalidada, então vem do cache. Rebuild ≈ 12 s.
- **Ordem ruim**: o `COPY . .` vem antes. Ele invalida, e a cascata leva o
  `npm ci` junto. Rebuild ≈ 54 s.

Mesma imagem, mesmas dependências, mesmo resultado final. **Quatro vezes mais
lento**, a cada commit, para sempre.

<Callout type="why" label="A regra prática">
Ordene as instruções da que **muda menos** para a que **muda mais**. Manifesto de
dependências antes do código-fonte, sempre — porque `package.json` muda uma vez
por semana e `src/` muda dez vezes por hora.
</Callout>

É exatamente o que os Dockerfiles desta stack fazem. No `worker-py`:

```dockerfile
# Instala SÓ as dependências, montando apenas o lockfile.
RUN --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project --no-dev

# Só agora o código entra.
COPY . /app
RUN uv sync --locked --no-dev
```

<Term word="BuildKit" alt="BuildKit">
O motor de build que substituiu o antigo construtor do Docker e hoje é o padrão.

Três diferenças mudam o dia a dia: ele monta o Dockerfile como um **grafo** e
constrói stages independentes em paralelo; ele aceita `RUN --mount`, que dá
cache e arquivos ao comando sem deixá-los na imagem; e ele pula stages que o
alvo pedido não precisa.

É também por isso que um Dockerfile com `RUN --mount=type=cache` não constrói no
construtor antigo: a sintaxe não existe lá.
</Term>

## Os mounts do BuildKit

Aqui está o que muita gente não sabe existir. `RUN --mount` resolve dois problemas
que camadas sozinhas não resolvem.

### `type=cache` — persiste ENTRE builds

Uma camada guarda o resultado de um build. Um cache mount guarda um diretório que
**sobrevive à invalidação da camada**:

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/api-go .
```

Mesmo quando a camada invalida e o `go build` roda de novo, o cache de compilação
do Go continua lá. O rebuild recompila só o que mudou, em vez do módulo inteiro.
O diretório **não** vai para a imagem final — ele vive no builder.

Vale para todo gerenciador de pacotes: `/root/.npm`, `/root/.cache/uv`,
`/var/cache/apt`, `~/.m2`.

### `type=bind` — usa um arquivo sem copiá-lo

```dockerfile
RUN --mount=type=bind,source=go.mod,target=go.mod \
    --mount=type=bind,source=go.sum,target=go.sum \
    go mod download
```

O arquivo fica visível durante o `RUN` e **não vira camada**. Sem isso você
precisaria de um `COPY go.mod go.sum ./`, que cria uma camada só para ser
descartada depois.

### `type=secret` — já visto na lição anterior

Existe pelo mesmo motivo: dar acesso a um arquivo durante o `RUN` sem que ele
persista em lugar nenhum.

## Multi-stage builda em paralelo

O BuildKit constrói um grafo de dependências, não uma lista. Stages que não
dependem uma da outra rodam **ao mesmo tempo**:

```dockerfile
FROM golang:1.25-alpine AS build-api      # ─┐
RUN go build …                            #  │ estas duas rodam
FROM node:22-alpine AS build-web          #  │ em paralelo
RUN npm run build                         # ─┘

FROM alpine AS final                      # espera as duas
COPY --from=build-api /out/api /api
COPY --from=build-web /app/dist /srv
```

E stages não alcançadas pelo alvo escolhido **nem são construídas**. Quando o
`sizes.sh` roda `--target minimal`, a stage `debug` é ignorada por completo.

## Quando o cache atrapalha

O cache é otimista por design, e isso tem um custo:

```bash
docker build --pull        # rebaixa a base: busca a tag de novo no registry
docker build --no-cache    # ignora TUDO: reexecuta cada instrução
```

`--pull` é o que você quer no CI noturno: pega a base atualizada com os patches de
segurança. `--no-cache` é o martelo — use para depurar um build que "funciona só
na minha máquina".

<Callout type="trap" label="Cache acerta, CVE permanece">
`RUN apt-get upgrade` numa camada em cache **não** aplica atualização nenhuma: o
texto do comando não mudou, então a camada de seis meses atrás é reaproveitada
inteira. Sua imagem parece atualizada e não está. Por isso builds de produção
rodam `--pull` periodicamente e o CI escaneia o resultado.
</Callout>

## Cache no CI, onde não existe disco local

No seu laptop o cache vive em `/var/lib/docker`. Num runner de CI, que nasce e
morre a cada job, não existe nada disso — por padrão, **todo build no CI é um
build frio**.

A saída é exportar o cache para um backend externo:

```yaml
- uses: docker/build-push-action@v7
  with:
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

`mode=max` é o detalhe que importa: o padrão (`min`) só guarda as camadas da
imagem final. Num Dockerfile multi-stage, isso significa **descartar exatamente as
camadas de build que custam caro**. Com `mode=max`, todas as stages são
preservadas.

## O que fica

- Invalidou uma camada, invalidam todas abaixo dela. Essa é a regra toda.
- Ordene do que muda menos para o que muda mais; dependências antes do código.
- `RUN` faz cache pelo TEXTO do comando, não pelo resultado — cuidado com `update`.
- `--mount=type=cache` sobrevive à invalidação; `type=bind` evita camadas inúteis.
- Stages independentes buildam em paralelo; stages não usadas nem buildam.
- No CI, `cache-to: type=gha,mode=max` ou o build é sempre frio.

<RunIt title="Meça o custo da ordem errada">

```bash
cd $(mktemp -d) && npm init -y >/dev/null && npm i --package-lock-only express >/dev/null
echo "console.log('oi')" > index.js

# Ordem RUIM: o código-fonte antes do install.
cat > Dockerfile.ruim <<'EOF'
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci --omit=dev
EOF

# Ordem BOA: o manifesto antes, o código depois.
cat > Dockerfile.boa <<'EOF'
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
EOF

# Aquece o cache dos dois.
docker build -q -f Dockerfile.ruim -t t/ruim . && docker build -q -f Dockerfile.boa -t t/boa .

# Agora edita SÓ o código-fonte — o cenário de todo dia.
echo "console.log('mudou')" > index.js

echo "── ordem ruim:" && time docker build -q -f Dockerfile.ruim -t t/ruim .
echo "── ordem boa:"  && time docker build -q -f Dockerfile.boa  -t t/boa  .

docker rmi t/ruim t/boa
```

</RunIt>
