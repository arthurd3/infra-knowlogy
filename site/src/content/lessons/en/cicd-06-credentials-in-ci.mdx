Jenkins masks credentials in the console. You see `****` and conclude the secret
is protected.

It is protected **from appearing in that shape**. That is a smaller promise than
it looks, and the example everyone uses to explain it is out of date.

<MaskingReality />

## What we measured

The circulating version says: *"`echo $TOK | base64` leaks the secret, because
Jenkins only looks for the literal value"*.

On Jenkins 2.568.3 with `credentials-binding` 728 that is **false**. The plugin
registers common encoded forms too, and base64 comes out masked.

But reversing the string goes through. Truncating goes through. Removing the
hyphens goes through. Spacing out the bytes goes through.

<Callout type="why" label="The right conclusion is worse than the wrong one">
If the problem were "Jenkins only knows the literal", the fix would be obvious:
teach it more shapes.

The real problem is different. Masking is **pattern matching over a known set of
representations**, and the set of possible transformations is infinite. No
version of the plugin closes that.

Masking is log hygiene: it stops the accident, the careless `echo`, the forgotten
`set -x`. Treating it as a security boundary is trusting a door that only locks
when the burglar uses the handle.
</Callout>

## A secret is a file, never an environment variable

This stack has one convention, and it holds in `config.go`, in `config.py` and
now in Jenkins: `<VAR>_FILE` pointing at `/run/secrets/`.

```yaml
# cicd/controller/casc/credentials.yaml
credentials:
  system:
    domainCredentials:
      - credentials:
          - string:
              id: "registry-token"
              secret: "${registry_token}"   # contents of /run/secrets/registry_token
```

`${registry_token}` is resolved by JCasC's file SecretSource, because the
Dockerfile sets `SECRETS=/run/secrets`. No secret shows up in `environment:`, in
`docker inspect` or in `/proc/<pid>/environ`.

<Callout type="trap" label="When upstream does not honour your convention">
The `jenkins/inbound-agent` entrypoint accepts `JENKINS_SECRET` with the **value**
in the variable, and has no `_FILE` support.

There were two ways out: writing "except here" into the convention, or six lines
of wrapper that read the file and export it. The six lines won.

A security convention with one documented exception is a convention with an
exception. With two, it is a suggestion.
</Callout>

## The asymmetry with managed CI

Here the cosign key is a file somebody generates, protects and rotates. On GitHub
Actions signing is **keyless**: the identity is the workflow's own OIDC token,
and there is no private key to leak.

That is the strongest argument for managed CI, and it is not about convenience.

<Callout type="danger" label="And the argument against, with a date">
In March 2025 the `tj-actions/changed-files` Action was compromised: tags v1
through v45.0.7 were rewritten to point at a malicious commit that scanned the
runner process memory and printed AWS keys, PATs and RSA keys into the log — in
base64, precisely because GitHub's masking compares the literal value. Over
23,000 repositories affected.

Both models have surface. The managed one's belongs to whoever you depend on; the
self-hosted one's is entirely yours. The choice is not "which is secure", it is
**which risk you would rather administer**.
</Callout>

The `credential-probe` job prints the same secret in six shapes. Run it and read

Before running: **which of the six would you expect to go through?** And after

<Fragment slot="hint">
The second question is the one that matters. If masking is not a boundary, what
is?
</Fragment>

<Fragment slot="answer">

Four go through: reversed, truncated, hyphen-stripped and spaced. Base64 and the
literal are masked.

What changes in a real pipeline is not trying to guess transformations. It is
ceasing to depend on masking at all:

- **Shrink the window.** A short-lived credential beats a masked one. What no
  longer exists cannot leak.
- **Shrink the scope.** A token that can only publish to one repository is worth
  nothing anywhere else when it leaks.
- **Do not put the secret where it can be printed.** Jenkins' `withCredentials`
  and BuildKit's `--mount=type=secret` exist so the secret never becomes a
  visible variable or an image layer.
- **Assume the log is public.** If that assumption breaks your design, the design
  is what needs changing.

And this module's gate locks in all three claims from this lesson: that the
literal is masked, that base64 is too, and that the reversed form goes through.
If any of them changes in a future Jenkins, it fails — and the lesson stops
lying.

</Fragment>
</LabExercise>

## What to take away

- Masking catches the literal and common encoded forms. It does not catch the rest.
- It is not a security boundary: it is log hygiene against accidents.
- A secret is a mounted file. A convention with two exceptions is a suggestion.
- Keyless (OIDC) is managed CI's real advantage; `tj-actions` is its price.
- Short lifetime and narrow scope are worth more than any masking.
