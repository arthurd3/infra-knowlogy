The whole port lives in `k8s/base/` — plain YAML, no Helm, aggregated by a
`kustomization.yaml` and applied with `kubectl apply -k`. The translation is
mechanical on the surface and full of physics underneath. This lesson walks
both layers.

## The translation map

| In Compose | In Kubernetes | Where |
|---|---|---|
| `services.api` | Deployment + Service | `k8s/base/api/` |
| `services.db` (named volume) | **StatefulSet** + volumeClaimTemplate | `k8s/base/db/` |
| `services.cache` (named volume) | Deployment + PVC | `k8s/base/cache/` |
| `networks:` edge/data/egress | **NetworkPolicies** | `k8s/base/network-policies/` |
| `secrets:` (file) | Secret mounted at `/run/secrets/` | generated by `k8s-up.sh` |
| `deploy.resources.limits` | `resources.limits` | on each workload |
| `cap_drop`/`read_only`/no-new-privileges | `securityContext` | on each workload |
| `stop_grace_period` | `terminationGracePeriodSeconds` | on each workload |
| port published on 127.0.0.1 | NodePort + kind's `extraPortMappings` | `k8s/kind/kind-config.yaml` |

Two things **did not change**: the images (they are the same ones, loaded into
the cluster with `kind load`) and the application. The api still reads
`POSTGRES_PASSWORD_FILE=/run/secrets/postgres_password`; what changed is who
mounts the file there — Compose mounted it from `stack/secrets/`, the kubelet
mounts it from a Secret **generated from the very same file** by `k8s-up.sh`.
Single source, zero drift.

## The cost in lines, measured

ADR 0001 argued that Kubernetes YAML describes the same thing with more
concepts. Now it can be measured. Counting non-empty, non-comment lines
(`grep -vc '^\s*#\|^\s*$'`):

| The `api` service | lines |
|---|---|
| `api` block in `compose.yaml` + the `compose.prod.yaml` overlay | **34** |
| `deployment.yaml` + `service.yaml` + `network-policies/api.yaml` | **96** |

Almost **3×** — and it is a trade, not waste. The 96 lines declare things the
34 left implicit: how many replicas, what "ready" means, who may talk to whom
port by port, what happens during an update. Compose was shorter because it
decided less.

<Callout type="why" label="Why plain YAML and not Helm">
Because the final YAML is the teaching material. Templating hides exactly the
file this lesson needs to show. `kubectl apply -k` (built-in kustomize) gives
us the aggregator without introducing a template language. See docs/adr/0007.
</Callout>

## DNS: the part that ported itself

In the Docker module, every named bridge network has a built-in DNS that
resolves service names. In Kubernetes, a **Service** named `db` becomes the DNS
name `db` inside the namespace. Practical consequence: the edge's Caddyfile —
which talks to `api:8080` and `web:8080` — was mounted into the cluster
**without changing a byte**. It is the same file from
`stack/services/edge/Caddyfile`, turned into a ConfigMap by `k8s-up.sh`.

<RunIt title="Prove the name resolves the same in both worlds">

```bash
# Compose:
docker compose -f stack/compose.yaml -f stack/compose.prod.yaml \
  exec worker getent hosts db

# Kubernetes:
export KUBECONFIG=k8s/.kubeconfig
kubectl -n infra-knowlogy exec deploy/worker -- getent hosts db
# different IPs, identical contract: "db" resolves where the application needs it.
```

</RunIt>

## Trap #1: the kubelet ignores HEALTHCHECK

In the Docker module we defined the api's health **inside the image**
(`HEALTHCHECK` instruction in the Dockerfile) and Compose inherited it — we
praised that at the time: "defining health next to the artifact beats
scattering it across orchestrators". Kubernetes disagrees head-on: **the
kubelet ignores the image's HEALTHCHECK**. Without probes declared in the
manifest, a pod with a hung process stays `Running` and `Ready`, receiving
traffic.

<RunIt title="See the instruction exist in the image and vanish in the pod">

```bash
docker image inspect infra-knowlogy/api-go:dev \
  --format '{{json .Config.Healthcheck}}'   # it is there, baked into the image

export KUBECONFIG=k8s/.kubeconfig
kubectl -n infra-knowlogy describe pod -l app=api | grep -iE 'liveness|readiness'
# what shows up here came from deployment.yaml — and from NOWHERE else
```

</RunIt>

That is why the api's `deployment.yaml` declares explicit `livenessProbe` and
`readinessProbe` — and the difference between the two is the entire subject of
lesson 3.

## Networks become NetworkPolicy — and trap #2

In Compose, topology was **positional**: `db` only sat on the `data` network
(with `internal: true`), so the edge could not reach it and it could not reach
the internet. In Kubernetes every pod sees every pod by default; topology must
be **declared**. The mirror lives in `k8s/base/network-policies/`: a
`default-deny` for the whole namespace and one policy per service giving back
only the strictly necessary — the same design as `compose.prod.yaml`, now at
the network layer.

```bash
# module 1's mirror proof, in both worlds:
docker compose -f stack/compose.yaml -f stack/compose.prod.yaml \
  exec edge sh -c 'nc -z -w2 db 5432'                       # fails
kubectl -n infra-knowlogy exec deploy/edge -- nc -z -w2 db 5432   # fails the same
```

<Callout type="trap" label="A green probe does not prove reachability">
During the port, `web` was left without its own policy — only the default-deny.
The site answered **502** behind the edge… with the web pod **Ready and
healthy**. How? The kubelet's probe originates on the **node**, not in another
pod, and does not traverse NetworkPolicies. The pod swore it was fine while no
neighbor could talk to it. The moral: a probe measures the pod from within;
pod-to-pod reachability is only proven by real traffic (or by the gate).
`k8s-verify` tests the full path from the outside for exactly this reason.
</Callout>

The worker remains the studied exception: its policy allows egress to the
internet (ports 80/443), **except** private ranges and link-local
(`169.254.0.0/16`, home of cloud metadata endpoints). It is defense in depth
underneath the application's SSRF guard — if the guard ever regresses, the
network still holds, and `k8s-verify` tests both layers.

## Trap #3: a fresh PV is born owned by root

Docker-module trap 10: a named volume inherits the owner of the directory that
already exists in the image. Its Kubernetes cousin: a fresh PersistentVolume is
born **owned by root**, and the Redis entrypoint — which in Compose never even
needed to chown — tried `chown /data` and died in CrashLoopBackOff, because we
had dropped the CHOWN capability. The portable fix is in
`cache/deployment.yaml`:

```yaml
securityContext:
  runAsUser: 999      # the image's `redis` user — the entrypoint skips its root branch
  fsGroup: 1000       # the kubelet fixes the volume's group at mount time
```

A better outcome than the original: the cache runs with
`capabilities.drop: [ALL]` **giving none back** — under Compose it needed
SETGID/SETUID for the entrypoint to switch users.

## What the port does not solve

`kubectl apply -k` instead of `docker compose up` does not change the nature of
production problems — it changes where they are declared. Resources are still
capped (now in `resources.limits`), the rootfs is still read-only (now in
`securityContext`), the secret is still a file that never shows up in `env`
(`k8s-verify` checks the spec and the process). Anyone who did module 1
recognizes every piece — that is the point of porting the same stack.

<RunIt title="Compare both worlds side by side, running together">

```bash
make up        # the Compose stack at http://127.0.0.1:8080
make k8s-up    # the SAME stack in a kind cluster at http://127.0.0.1:8081
curl -s http://127.0.0.1:8080/edge-health -o /dev/null -w '%{http_code}\n'
curl -s http://127.0.0.1:8081/edge-health -o /dev/null -w '%{http_code}\n'
```

</RunIt>
