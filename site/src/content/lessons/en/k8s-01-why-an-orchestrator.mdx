The Docker module ended with a recorded decision: **Compose, not Kubernetes**
(ADR 0001). That decision came with an honest list of what we were giving up —
Compose does not recreate a container that disappeared, does not deploy without
downtime, does not reschedule anything when a machine dies. And it came with a
prescription for the future:

> a future module on orchestration must port **this same stack** to Kubernetes,
> not introduce a new one — the side-by-side comparison is only honest because
> the application is the same.

This module is that prescription, fulfilled. The same six services — `edge`,
`api`, `worker`, `web`, `db`, `cache` —, the same images built by the same
Dockerfiles, the same Caddyfile without changing a single line. What changes is
the orchestrator underneath. And, as everywhere else in this repository, every
item on that list of limits becomes a **measured number**, not a marketing line.

## The cluster fits in a container

We use **kind** (Kubernetes-in-Docker): the cluster "node" is a Docker container
running kubelet, containerd and the whole control plane. Nothing is installed on
the host beyond two binaries (`kind`, `kubectl`), and destroying the cluster
means destroying a container.

```bash
make k8s-up      # creates the cluster, loads the images, applies the manifests
make k8s-down    # deletes everything, no trace left behind
```

On the machine this module was written on, measured by `make k8s-verify`
(the numbers live in `site/src/data/k8s-measured.json`): creating the cluster
from scratch until the node was ready took **25 s**; from `kubectl apply` until
all six services answered health, **22 s**. It is not instant like
`docker compose up`, and it does not have to be — what those seconds buy is the
subject of this lesson.

<Callout type="why" label="Why kind and not minikube/k3s">
kind runs the cluster inside containers — which is exactly what module 1 is
about —, creates and destroys in seconds, and is the testing tool of the
Kubernetes project itself. And there is a hard requirement: **kind ≥ 0.23**,
because before that NetworkPolicy was accepted by the API and silently ignored.
From 0.23 on, the built-in CNI enforces the policies — and the module's gate
proves it in practice. See docs/adr/0007.
</Callout>

## What Compose already did just as well

Let us be fair before selling the orchestrator. If the worker's **process**
dies, Docker with `restart: unless-stopped` resurrects it — and so does the
kubelet (`restartPolicy: Always`). Process crashes are not the differentiator;
both recover.

The difference starts when the problem is not the process but the **whole
container** — or the machine underneath it.

## Proof 1 — the controller recreates what disappeared

In Compose, `docker rm -f` on a container is final: the restart policy lives in
the container, and a removed container has nobody left to defend it. It only
comes back when someone runs `docker compose up` again. In Kubernetes, the pod
is not the unit you manage — the **Deployment** declares "I want 2 replicas of
the api", and a controller compares desire with reality all the time.

`k8s-verify` deletes an api pod and times until the replacement is **Ready**:
**2 s**.

<RunIt title="Delete a pod and watch the controller replace it">

```bash
make k8s-up
export KUBECONFIG=k8s/.kubeconfig

kubectl -n infra-knowlogy get pods -l app=api
kubectl -n infra-knowlogy delete pod <one-of-the-api-pods> &
kubectl -n infra-knowlogy get pods -l app=api --watch
# a new pod shows up BEFORE the old one finishes dying

# the equivalent in the Docker module:
docker compose -f stack/compose.yaml -f stack/compose.prod.yaml up -d
docker rm -f infra-knowlogy-api-1
docker compose -f stack/compose.yaml ps api   # gone; nobody recreates it
```

</RunIt>

It is the same mechanism that answers for a dead machine: in a real multi-node
cluster, the pods of the lost node are rescheduled onto the living ones. The
single-node kind cluster cannot demonstrate that — but the mechanism that does
it is literally what you just watched.

## Proof 2 — restarts are counted, not silent

In the Docker module, `restart: unless-stopped` recovers crashes **silently**:
the container restarts and, unless you compare `docker ps` before and after,
nothing records that it happened. Kubernetes exposes the counter:

```text
NAME                      READY   STATUS    RESTARTS      AGE
worker-54f54d8f9b-d4t8k   1/1     Running   1 (12s ago)   9m
```

`k8s-verify` terminates the worker's process from the inside and checks that
`restartCount` incremented. A service that restarts every night stops being a
legend ("I think it crashes sometimes?") and becomes a number in
`kubectl get pods`.

<Callout type="trap" label="SIGKILL on PID 1 does not work — again">
The first version of that test ran <code>os.kill(1, 9)</code> from inside the
container. Nothing happened: the kernel **ignores SIGKILL sent to PID 1 from
within its own namespace** — the same special signal handling that lesson 3 of
the Docker module measured around <code>docker stop</code>. The test uses
SIGTERM, which is delivered because the worker installs a handler. PID 1
physics does not change with the orchestrator.
</Callout>

## Proof 3 — deploying without dropping anyone

This was the most expensive item on ADR 0001's list. In Compose, swapping the
api image means `up -d --force-recreate`: the old container dies, the new one
boots, and whoever was mid-request gets the error in the face. In Kubernetes,
the api Deployment declares:

```yaml
replicas: 2
strategy:
  type: RollingUpdate
  rollingUpdate: {maxUnavailable: 0, maxSurge: 1}
```

"Never go below 2 ready replicas; create the new one BEFORE killing the old
one." `k8s-verify` runs a request loop against the api **during** a
`kubectl rollout restart` and counts the failures: **27
requests, 0 failed**.

<RunIt title="Watch a deploy with traffic flowing through it">

```bash
export KUBECONFIG=k8s/.kubeconfig
CODE=$(curl -s -X POST http://127.0.0.1:8081/api/links \
  -H 'content-type: application/json' -d '{"url":"https://example.com/"}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["code"])')

while :; do curl -s -o /dev/null -w '%{http_code} ' \
  "http://127.0.0.1:8081/api/links/$CODE"; sleep 0.1; done &

kubectl -n infra-knowlogy rollout restart deployment/api
kubectl -n infra-knowlogy rollout status deployment/api
kill %1   # nothing but 200s in the terminal — no request hit the floor
```

</RunIt>

<Callout type="trap" label="Zero downtime requires the application to cooperate">
The first version of this test dropped **1 request out of 26**. Cause: SIGTERM
reaches the pod BEFORE kube-proxy stops sending new connections to it, and the
api closed its listener immediately — whoever landed in that propagation window
got connection refused. The fix lives in the api itself
(<code>SHUTDOWN_DELAY=2s</code>): on SIGTERM it keeps serving for 2s before
closing. The textbook calls this a preStop sleep — which does not exist in a
distroless image, because there is no shell to run <code>sleep</code>. The
orchestrator promises the rolling; the application delivers the "zero
downtime".
</Callout>

<Term word="Reconciliation loop" alt="reconciliation loop">
The mechanism that makes Kubernetes different from a deploy script. A
controller sits in a perpetual loop comparing two things:

- the **desired** — what is in the objects you applied;
- the **actual** — what really exists in the cluster.

When they diverge, it acts to bring them together, and compares again. There is
no "the deploy finished": there is continuous convergence.

That is why deleting a pod by hand is not a destructive operation — it is a
divergence, and the controller undoes it. And it is also why a cluster does not
"get lost": it holds no sequence of steps that could be interrupted halfway.
</Term>

  whenB="From the moment somebody has to be woken at night because a process died. Two-second self-healing pays for learning the model."
>
  <Fragment slot="a">

  </Fragment>
</Tradeoff>

<FieldNote
  source="Kubernetes Docs — Kubernetes Components"
  url="https://kubernetes.io/docs/concepts/overview/components/"
  accessed="2026-09-20"
>
The documentation describes the control plane as a set of independent
controllers, each responsible for one object type, all running the same
reconciliation loop. The architecture is deliberately decentralised: there is no
single orchestrator that knows the whole state. Not measured here — this cluster
runs everything as one process per container, and the controllers' independence
only shows when one of them fails on its own.
</FieldNote>

## The verdict stays the same

None of this revokes ADR 0001. A well-configured host running Compose still
serves the majority of projects, and the list above is exactly the decision
criterion: when "a container that disappears must come back on its own",
"restarts must be auditable" and "a deploy must not drop requests" become
requirements of YOUR system — that is where the orchestrator pays its own cost.
Before that, it is extra YAML.

The rest of the track shows **how** the port was done: lesson 2 translates each
block of `compose.yaml` into its Kubernetes counterpart, and lesson 3 dissects
probes — home of the most misunderstood difference between the two worlds.
