The most damaging sentence in this area is short: *"I marked it sensitive, so it
is protected"*. It is false, and this module's gate measures exactly where.

<SecretPaths />

## What `sensitive` does, and what it does not

It changes **command-line output**. Where the value would appear, you get
`(sensitive value)`. That has real value: it keeps the password out of the CI
log, out of the screenshot, out of the Slack channel where the plan was pasted.

And it changes **nothing at all** about what is written to state or to a saved
plan.

<Callout type="danger" label="The two files nobody remembers">
State is the first. The **saved plan** is the second, and the more forgotten one:
it is the complete list of attributes with values, and it usually becomes a build
artifact — kept for 90 days, downloadable by anyone with pipeline access.

That is why OpenTofu's encryption has separate blocks for `state` and for `plan`.
Encrypting only one of them solves half the problem.
</Callout>

## The path this repository uses

In module 4, the Postgres password **is not** in state. The gate proves it, and
the reason is no security setting at all: it is the `<VAR>_FILE` convention.

```hcl
env = ["POSTGRES_PASSWORD_FILE=/run/secrets/postgres_password"]

volumes {
  host_path      = "${var.host_repo_root}/stack/secrets/postgres_password"
  container_path = "/run/secrets/postgres_password"
  read_only      = true
}
```

`tofu` passes a path. The one who opens the file is the Postgres entrypoint,
already inside the container. **The value never crosses the tool** — and what is
never read cannot be written down.

<Callout type="why" label="Why this beats encrypting">
Encryption protects the file. The `<VAR>_FILE` convention keeps the secret from
**entering** the file.

These are defences at different layers, and the second is cheaper: no key to
rotate, no key provider to configure, no way to misconfigure it and find out
later. The best way not to leak a secret through state remains the secret never
having been there.
</Callout>

## And when the secret has to go in?

It happens, and it is legitimate: a `random_password` generated by the tool
itself, a token a resource hands back on creation, a key that only exists after
`apply`. No convention saves you there — the value is a resource attribute.

The `iac/demo-secret/` folder exists to measure that case, deliberately:

```hcl
resource "terraform_data" "leaked" {
  # the WRONG way, on purpose
  input = file(var.password_file)
}
```

<RunIt>
```bash
cd iac/demo-secret && tofu init && tofu apply -auto-approve
grep -c "$(cat ../../stack/secrets/postgres_password)" terraform.tfstate
# 2
```
</RunIt>

Two occurrences, in plaintext. That is the number the gate checks.

## OpenTofu's state encryption

It landed in 1.7 (April 2024) and **does not exist** in Terraform's open source
CLI — it is the most concrete difference between the two, and the practical
reason this module uses OpenTofu.

```hcl
terraform {
  encryption {
    key_provider "pbkdf2" "k" {
      passphrase = var.passphrase
    }
    method "aes_gcm" "m" {
      keys = key_provider.pbkdf2.k
    }
    state { method = method.aes_gcm.m }
    plan  { method = method.aes_gcm.m }
  }
}
```

With it on, the same `grep` from the example above returns **zero**, and the
file stops being a JSON of resources:

```json
{
  "serial": 1,
  "lineage": "430fce…",
  "meta": { "key_provider.pbkdf2.k": "eyJzYWx0Ijoi…" },
  "encrypted_data": "…",
  "encryption_version": "v0"
}
```

<Callout type="trap" label="Migrating plaintext state needs the fallback">
Turning encryption on in a directory that already has **unencrypted** state
fails: OpenTofu cannot read what is already there. The migration needs an
`unencrypted` method as a `fallback`, which is dropped after the first write.

Without it the error talks about a *lock* and a *backup file*, sending you to
look at concurrency when the problem is format.
</Callout>

And the proof that closes it: without the key, `tofu` **refuses** to read.

```
Error: Unsupported state file format: This state file is encrypted
and can not be read without an encryption configuration
```

<Tradeoff
  a="Encrypt the state"
  b="Keep the secret from reaching it"
  whenA="When the value is generated by the tool itself or handed back by a resource on creation — there is no way for it not to pass through. It costs a key to manage and rotate."
  whenB="When the secret already exists outside and only needs <b>delivering</b>: a file path, a vault reference, a write-only argument. Zero key cost, and nothing to rotate."
  chose="b"
  verdict="the <code>&lt;VAR&gt;_FILE</code> convention across the whole stack, with encryption demonstrated and measured alongside — because the case that needs it does exist."

/>

>
Terraform took a different route: `ephemeral` (1.10, November 2024) and
*write-only* arguments (1.11, February 2025) let a provider **use** a secret
during an operation without it ever being recorded. It is the same philosophy as
the `<VAR>_FILE` convention, only inside the language — and it covers cases a
file path cannot.
</FieldNote>

<LabExercise check="com TF_ENCRYPTION o estado vira envelope" file="tools/scripts/iac-verify.sh">

The gate turns encryption on through an environment variable (`TF_ENCRYPTION`)
rather than writing the `encryption` block into a `.tf` file.

Question: why? Wouldn't the block in the file be clearer?


<Fragment slot="hint">
Think about what would have to be written inside the block for it to work.
</Fragment>

<Fragment slot="answer">

Because the block needs the **passphrase**, and a `.tf` file is versioned.

Writing the passphrase there would commit the key next to what it protects — the
IaC version of leaving the password on a sticky note on the monitor. You can use
`var.passphrase`, but then the value has to come from somewhere at run time,
which is exactly what the environment variable already does.

There is a second reason, specific to the gate: it has to measure **both**
states — the same directory, the same configuration, encrypted and not. With
encryption in the file, comparing would mean editing `.tf` mid-run. With the
variable, the only thing that changes between the two measurements is it:

```bash
tofu apply -auto-approve                        # plaintext state
TF_ENCRYPTION="$ENC" tofu apply -auto-approve   # same directory, encrypted
```

In production neither form is the final answer: the passphrase would become a
KMS key provider — AWS, GCP, Azure Vault or OpenBao — and then there would be no
passphrase to keep at all.

</Fragment>
</LabExercise>

## What sticks

- `sensitive = true` changes the **screen**, not the file.
- There are **two** files: the state and the saved plan. Encrypt both, or
  neither.
- The `<VAR>_FILE` convention keeps the secret out — and is cheaper than
  encrypting.
- When the value is born inside the tool, there is no avoiding it: encrypt then.
- State encryption exists in OpenTofu (1.7) and not in the Terraform CLI.
  Terraform's route was `ephemeral` and write-only.
- Migrating plaintext state requires an `unencrypted` `fallback`.
