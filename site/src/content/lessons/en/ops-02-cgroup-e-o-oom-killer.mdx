A container has no memory. It has a **limit**.

The difference sounds philosophical right up until an application reads
`/proc/meminfo`, finds 31 GiB, and sizes its heap accordingly.

<CgroupLimit />

## The two questions, measured

```console
$ docker exec infra-knowlogy-worker-1 head -1 /proc/meminfo
MemTotal:       32787392 kB          ← 31 GiB: the HOST's memory

$ docker exec infra-knowlogy-worker-1 cat /sys/fs/cgroup/memory.max
402653184                            ← 384 MiB: THIS container's limit
```

The `/proc` inside the container **is not isolated** for memory. The mount
namespace cropped the filesystem, but `/proc/meminfo` is generated by the kernel
from global state — and there is no memory namespace.

<Term word="cgroup" alt="control group">
*Control group* — the kernel mechanism that **limits and accounts for** a set of
processes' resources. It is the container's other half: the namespace crops what
the process *sees*, the cgroup caps what it *consumes*.

In version 2 (the only one on modern Fedora, and the one Kubernetes has required
since 1.25) each cgroup is a directory and each limit is a file:

```
/sys/fs/cgroup/memory.max      the hard ceiling — crossing it is SIGKILL
/sys/fs/cgroup/memory.high     the pressure ceiling — crossing it is slowness
/sys/fs/cgroup/memory.current  how much is in use right now
/sys/fs/cgroup/cpu.max         "100000 100000" = 1 CPU (quota per period)
/sys/fs/cgroup/pids.max        how many processes may exist
```

Inside the container these paths describe **the container itself** — the only
reliable way for an application to discover its own limit.
</Term>

## `memory.max` and `memory.high` are not the same thing

Measured on this stack's `worker`:

```console
memory.max   = 402653184   (384 MiB)
memory.high  = max          (no pressure ceiling)
```

- **`memory.max`** is the hard ceiling. Reaching it triggers the OOM killer.
- **`memory.high`** is the pressure ceiling. Crossing it does **not** kill: the
  kernel forces aggressive reclaim and *throttles* the process. The result is a
  service that gets slow instead of dying.

Docker exposes the first (`--memory`) and not the second. Anyone wanting
degradation rather than death has to write to the cgroup by another route — and
it is a choice almost nobody knows they have.

## What happens when the limit is crossed

```console
$ docker run --name oom --memory=64m --memory-swap=64m python:3.13-alpine \
    python -c 'b=[]
while True: b.append(bytearray(8*1024*1024))'

$ docker inspect oom --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
true 137
```

**Measured: 0.51 seconds from start to death.**

<Callout type="warn" title="137 = 128 + 9, and the 9 is what matters">
The shell convention is that a process killed by a signal exits with `128 +
signal number`. Signal 9 is `SIGKILL`.

`SIGKILL` is **not catchable**. There is no handler, `defer`, `finally`,
`atexit` or `trap` that runs. The connection is not closed, the temporary file
is not deleted, the transaction is not rolled back by the application — the
process simply stops existing between one instruction and the next.

Which is why "handling the OOM" is not a strategy. The strategy is **not getting
there**.
</Callout>

And the only proof left behind:

```console
$ cat /sys/fs/cgroup/memory.events
oom 1
oom_kill 1
```

A counter. No timestamp, no which-process, no how-much-it-asked-for. That is why
Docker's `OOMKilled=true` and Kubernetes's `reason: OOMKilled` are worth so much:
they preserve the fact the cgroup merely counts.

<Tradeoff
  a="A low, tight limit"
  b="A high, generous limit"
  whenA="When many containers share a node and you need a leak in ONE not to take the others down. The limit is damage containment, and the cost is dying earlier."
  whenB="When the service is the only thing that matters on that node and its legitimate memory peak is hard to predict. The cost is that a leak takes the whole machine with it."
>
  <Fragment slot="a">
    The OOM killer hits only the culprit, and the orchestrator restarts it. In
    exchange: legitimate peaks become deaths, and you pay in restarts.
  </Fragment>
  <Fragment slot="b">
    Fewer false deaths. In exchange: the HOST's OOM killer steps in, and it picks
    its victim by heuristic — it may well not be whoever caused the problem.
  </Fragment>
</Tradeoff>

## The application can, and should, read its own limit

Modern runtimes already do: the JVM has `-XX:+UseContainerSupport` (on by
default since Java 10), .NET reads the cgroup, Node accepts
`--max-old-space-size`. The ones that do not have to be told by hand.

The correct read, in any language, is the file — not `/proc/meminfo`:

```python
def my_memory_limit():
    """Reads THIS container's limit. Returns None when there is no limit."""
    try:
        v = open("/sys/fs/cgroup/memory.max").read().strip()
        return None if v == "max" else int(v)
    except FileNotFoundError:
        return None          # cgroup v1, or not in a container
```

<FieldNote
  source="Linux kernel documentation — Control Group v2"
  url="https://docs.kernel.org/admin-guide/cgroup-v2.html"
  accessed="2026-09-21"
>
The kernel documentation describes v2 as a deliberate rewrite of v1, motivated by
a design flaw: in v1 each resource had its own hierarchy, and a process could sit
at inconsistent positions in each of them. V2 imposes a **single hierarchy**. That
is why Kubernetes came to require it, and why the migration took so long — it was
not an incremental improvement, it was a different model. Not measured here: this
machine only has v2.
</FieldNote>

<LabExercise
  question="A container dies every so often with no log at all and no stack trace. How do you confirm it was the OOM killer and not the application?"
  check="OOM killer: OOMKilled=true e exit 137"
>
  <Fragment slot="hint">
    If there is no log, it is because the process never got to write one. The
    record is with whoever killed it, not with whoever died.
  </Fragment>
  <Fragment slot="answer">

```bash
# 1. The state Docker kept from the last death
docker inspect <container> --format '{{.State.OOMKilled}} {{.State.ExitCode}}'

# 2. On Kubernetes, the same fact under another name
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'

# 3. The kernel, which records the victim selection
sudo dmesg -T | grep -i -A2 'killed process'
```

`OOMKilled=true` with `137` closes the case. The absence of a log **is** the
evidence: SIGKILL leaves no chance to write anything, so an application crash
would produce a stack trace and an OOM produces nothing.

`dmesg` is what tells you **how much** the process was asking for and who the
other candidates were — the only source with that information, and it is lost on
reboot.

  </Fragment>
</LabExercise>
